# A3.6 Node 26.13.1 V8 trap-handler and Android signal-chain review

Reviewed 2026-11-27 against the pre-guard Android arm64-v8a candidate; updated with the guarded-candidate device follow-up below.

**Current disposition: A3.6 remains open.** The source-derived debuggerd-bypass risk applied to the pre-guard candidate described here. The Android guard patch removes Node's separate WebAssembly `SIGSEGV` wrapper from the guarded candidate, and the follow-up confirms basic runtime behavior on one Android 15/4 KB device. Dynamic vendor signal-symbol resolution and synchronous native-fault handling have not been verified.

For the pre-guard candidate, the default Node POSIX startup path could install Node's `SIGSEGV` WebAssembly wrapper even though V8's trap-handler support was compiled out. On stock AOSP Android 15, source traces the app-process `sigaction` lookup through ART's `libsigchain`; the Node registration replaces the chain's saved debuggerd action. If an ordinary native fault reached Node's wrapper, V8 would return “not handled” and Node's no-predecessor path would reset the disposition to `SIG_DFL` and raise. This was a source-level integration risk, not a device reproduction or proof of the exact vendor process's fault/tombstone result.

The address-space condition is important: `CanEnableWebAssemblyTrapHandler()` does not check V8's compile-time support. It accepts an unavailable or unlimited `RLIMIT_AS`; otherwise it compares the limit with V8's reservation-size query. With support off, that query returns Node's 64-KiB minimum probe, so this check passes whenever the process limit is at least 64 KiB. The target process's actual limit was not read. Node also does not check the return from `V8::EnableWebAssemblyTrapHandler(false)` before setting its configured flag.

## Android 15 ART chain: source trace and boundary

This is more than evidence that ART installs a signal-chain handler. The pinned AOSP Android 15 release sources describe the relevant call and replacement semantics:

1. Android's dynamic linker calls `linker_debuggerd_init()` during process startup ([Bionic `linker_main.cpp:324`](https://android.googlesource.com/platform/bionic/+/refs/tags/android-15.0.0_r1/linker/linker_main.cpp#L324)); that calls `debuggerd_init()` ([`linker_debuggerd_android.cpp:64–75`](https://android.googlesource.com/platform/bionic/+/refs/tags/android-15.0.0_r1/linker/linker_debuggerd_android.cpp#L64)). `debuggerd_init()` registers the debuggerd `SA_SIGINFO` action for `SIGSEGV` ([system/core `debuggerd_handler.cpp:749–763`](https://android.googlesource.com/platform/system/core/+/refs/tags/android-15.0.0_r1/debuggerd/handler/debuggerd_handler.cpp#L749); registration list in [`handler.h:81–96`](https://android.googlesource.com/platform/system/core/+/refs/tags/android-15.0.0_r1/debuggerd/include/debuggerd/handler.h#L81)).
2. The Android 15 `app_process` build includes `libsigchain`; its build comment says this puts `libsigchain` symbols ahead of libc for app libraries ([frameworks/base `cmds/app_process/Android.bp:52–56`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-15.0.0_r1/cmds/app_process/Android.bp#L52)). `libsigchain` is marked global specifically so classloader-loaded app libraries resolve its symbols before libc ([ART `sigchainlib/Android.bp:34–40`](https://android.googlesource.com/platform/art/+/refs/tags/android-15.0.0_r1/sigchainlib/Android.bp#L34)).
3. ART `FaultManager::Init(true)` registers a special `SIGSEGV` handler through `AddSpecialSignalHandlerFn()` ([ART `runtime/fault_handler.cc:110–130`](https://android.googlesource.com/platform/art/+/refs/tags/android-15.0.0_r1/runtime/fault_handler.cc#L110)). `SignalChain::Claim()` calls `Register()`, which installs ART's kernel handler while saving the currently installed action in `action_` ([`sigchain.cc:277–303`](https://android.googlesource.com/platform/art/+/refs/tags/android-15.0.0_r1/sigchainlib/sigchain.cc#L277)). Under the startup order above, that saved action is debuggerd's handler.
4. Once the signal is claimed, ART's `sigaction` shim updates the saved `action_` when a later caller registers a handler; it returns the old action only if the caller supplies a non-null `old_action` ([`sigchain.cc:547–589`](https://android.googlesource.com/platform/art/+/refs/tags/android-15.0.0_r1/sigchainlib/sigchain.cc#L547)). Node supplies `nullptr`, so its wrapper replaces the saved debuggerd action without retaining it. This is the stock AOSP Android 15 source path; whether the target vendor image resolves the candidate's call through the shim has not been observed on-device.
5. ART first tries its special handlers, then calls `android_handle_signal`, then forwards to `action_` ([`sigchain.cc:430–545`](https://android.googlesource.com/platform/art/+/refs/tags/android-15.0.0_r1/sigchainlib/sigchain.cc#L430)). The debuggerd special callback returns true only for recoverable permissive-MTE or GWP-ASan cases; otherwise it returns false ([system/core `debuggerd_handler.cpp:805–833`](https://android.googlesource.com/platform/system/core/+/refs/tags/android-15.0.0_r1/debuggerd/handler/debuggerd_handler.cpp#L805)). Thus a regular native fault would normally reach the saved debuggerd action. If Node's wrapper runs, V8 returns false and Node has no previous Node callback on the default startup path; its fallback writes `SIG_DFL` through the same claimed signal and raises. ART's chain action can then be DFL, whose handler path removes ART's kernel handler and returns so the fault recurs under the default disposition (`sigchain.cc:530–540`). **This establishes a source-derived debuggerd bypass risk for the traced stock AOSP path; it does not establish that the target device actually takes this path or what report the OS produces.**

The static conclusion depends on ordinary Node initialization, the wrapper's address-space check passing, no embedder-installed Node `SIGSEGV` callback, stock AOSP Android 15 signal-symbol ordering, and the candidate's call resolving through ART's shim. Candidate object/source evidence supports the Node side; it cannot verify the vendor OS, actual runtime symbol binding, app-supplied flags/callbacks, or crash output. The Node wrapper only installs `SIGSEGV` on this non-Apple POSIX path; test `SIGBUS` separately as a chain control.

## Evidence still required to close A3.6

### Android guard implementation and incremental candidate relink

- Added [`node-26-android-disable-wasm-signal-wrapper.patch`](../tool/android/patches/node-26-android-disable-wasm-signal-wrapper.patch), SHA-256 `904cbb593f09bbfede4692ce4d5f41e8652c0691942d10f155339caf9e083024`. It limits `NODE_USE_V8_WASM_TRAP_HANDLER` to Apple, Windows, and non-Android Linux. For Android, Node no longer compiles its separate `TrapWebAssemblyOrContinue` signal wrapper; V8 remains on its explicit Wasm bounds-check path.
- The patched Node `src/node.cc` SHA-256 is `dcea17aa75ca4d53ebed183a915de1b93c44a00c91a979cbd4c813ad5f336d44`; the pristine official source file was restored after the targeted compile. Source archive remains `a7f6204ff63b6a2cd274d48903285abb86ed53a99070e532d4c2fd787457d9e6`.
- Recompiled only `src/node.cc` for the existing arm64/API 24/NDK 30 build using its generated NDK Clang command, updated `libnode_base.a`, and reran the generated `libnode.so` link command. The new `node.o` SHA-256 is `07e9f98f31bfc718c57abd29f30b80b8e3a220b2ab8e0a93a30e618e508ca7c5`; the archive is `6d060d3dedb6acca2a192bf69c621336f84adf21853b0f4a6033e672751edfd8`; unstripped `libnode.so` is `bd565d18e9b9533d8350a0527e64277ba95ab398982c1e4679cb77fb12f3f65b`; the stripped APK copy is `53f042c7497b29b9fd15c5b413c30ace01a97dc3b26c1b6caebc7630dd4aff13`.
- `llvm-nm -C` found no `node::TrapWebAssemblyOrContinue` in the relinked library. `v8::TryHandleWebAssemblyTrapPosix` remains as a V8 symbol, and the `node.o` still references `sigaction`/`raise` for Node's other signal code; those facts do not show that the WebAssembly wrapper is installed. All three `PT_LOAD` segments remain aligned to `0x4000`.
- At the initial review cutoff, the disposable Debug APK described above had not been installed because ADB and wireless discovery were unavailable. That status was superseded by the 2026-11-27 USB-device follow-up below; the earlier unpatched Wasm smoke still does not transfer to this patched candidate.
- The successful object compile and link reuse the previously configured build tree. A full build in a differently rooted copy was stopped after it attempted to rebuild host tools and Apple `ld` rejected `--start-group`/`--end-group`; this incremental relink is not a clean source rebuild or build attestation.

## Evidence still required to close A3.6

1. On the LGE Android 15 arm64/4 KB device, the observable `sigaction` handler/flags returned before and after `node::Start()` were equal for SIGSEGV and SIGBUS. Loaded `libsigchain` symbol resolution, Node startup flags, `RLIMIT_AS`, and a supported-minimum API device remain unverified.
2. The patched candidate produced a catchable explicit Wasm out-of-bounds result and file/loopback results on that device. A test-only `raise(SIGSEGV)` produced `SI_TKILL` crash captures and one confirmed tombstone copy to DropBox. This is not a synchronous `SEGV_MAPERR`/`SEGV_ACCERR` memory-fault test; that signal-chain behavior remains unverified.
3. A clean same-path Node source rebuild exactly reproduced the pre-guard candidate. The guarded candidate itself still has only the targeted `node.cc` compile and incremental relink, so a clean rebuild of that exact patched binary plus formal build attestation remains open. Keep physical 16-KB-device execution as a separate gate; no such device is available.
4. Do not re-enable V8's signal trap handler without an independent V8 crash/security review and Android signal-chain review. V8's POSIX handler source explicitly requests crash-reporting/security review ([Node v26.13.1 `handler-inside-posix.cc:5–21`](https://github.com/nodejs/node/blob/v26.13.1/deps/v8/src/trap-handler/handler-inside-posix.cc#L5)). Node documents the inline-check behavior of [`--disable-wasm-trap-handler`](https://github.com/nodejs/node/blob/v26.13.1/doc/api/cli.md#L1092).

## 2026-11-27 USB-device follow-up: patched Node runtime smoke

- **Device and candidate:** LGE AN10, Android 15/API 35, arm64, `PAGE_SIZE=4096`. The installed isolated test APK SHA-256 was `56e8eedeef4193fde0b6b754f8bda3d5c7676c484de67011a772548fdf401490`; its packaged stripped `libnode.so` SHA-256 was `53f042c7497b29b9fd15c5b413c30ace01a97dc3b26c1b6caebc7630dd4aff13`. APK 16 KB zip alignment and v2 signature checks had passed before installation.
- **Node startup and probe:** `node::Start()` reached Node v26.13.1. The app-private result was `{"version":"v26.13.1","file":"ok","network":"network-ok","wasm":"explicit-bounds-check-trapped"}`. The test used explicit Wasm bounds checks; it did not exercise V8's signal trap handler.
- **Signal actions:** before/after snapshots were equal within the `:node` process: SIGSEGV handler `0x7661a4db14`, flags `402655236`; SIGBUS handler `0x763a0da878`, flags `4`. This records the action visible through the process `sigaction` API and does not independently identify the underlying kernel handler or prove which shared-library symbol supplied the call.
- **Injected crash and service restart:** the test harness then called `raise(SIGSEGV)`. Logcat recorded two `Fatal signal 11` events, both `code -6 (SI_TKILL)`, in successive `:node` PIDs. ActivityManager restarted the bound service after the first process death, so the unconditional test injection ran again. The captured system log confirms one `tombstone_29` copy to DropBox tagged `SYSTEM_TOMBSTONE`; it does not confirm a second copied tombstone before cleanup. No ordinary memory-access fault was injected.
- **Cleanup and disposition:** the probe package was force-stopped and uninstalled. The phone remained on the user's news app (`LiveRoomActivity`); its process was alive, and the probe package path was absent for user 0. The test-only service restart behavior is a fixture observation, not a product service contract. The result narrows the patched candidate's startup and crash-report evidence but does not close A3.6 or the vendor signal-chain gate.
