# A3.6 Android Node runtime survey: Termux package route (2026-11-20)

**Initial survey:** 2026-11-20 UTC. **Freshness and package addendum:** 2026-11-23. This extends the project’s existing [upstream release status](android-a3-upstream-android-runtime-status-2026-11-20.md); it does not replace the checks of nodejs-mobile, fogtape, or digidem.

## 2026-11-23 release freshness and package inspection

- The official [Node.js release list](https://nodejs.org/en/about/previous-releases) still marks v24 as LTS, and its [v24.22.3 release page](https://nodejs.org/en/blog/release/v24.22.3/) identifies the 2026-11-11 build as a security release. No later v24 release appears in the official release listings checked on 2026-11-23.
- The official [nodejs-mobile release listing](https://github.com/nodejs-mobile/nodejs-mobile/releases) still lists v18.20.4 as its latest release and provides Android artifacts for armeabi-v7a, arm64-v8a, and x86_64. The Node.js release-status page marks v18 EOL. It is not a maintained Node 24 Android artifact.
- Termux stable APT `Release` metadata is dated 2026-11-23 01:02:07 UTC and advertises `aarch64`, `arm`, `i686`, and `x86_64`. All four current `nodejs-lts` package records still say 24.22.3. The aarch64 `.deb` was fetched for read-only inspection; its SHA-256 `80edcc73db025db0baa09be27e3d65a16e6f2a72ab925f1873a1b808ab857c28` matches the repository package index.
- The aarch64 package contains `/data/data/com.termux/files/usr/bin/node`, Node headers, Corepack and Corepack shims. It contains no `libnode.so`, no bundled `.so` files, and no npm implementation; the package metadata recommends a separate `npm` package. The Node binary is a dynamically linked PIE executable with interpreter `/system/bin/linker64`, RUNPATH `/data/data/com.termux/files/usr/lib`, and 11 `DT_NEEDED` libraries. Its three `PT_LOAD` segments each use `p_align=0x4000` and have congruent file/virtual offsets. This is positive ELF alignment evidence for the standalone Termux executable, not APK/AAB or 16 KB device evidence.
- The current Aggregate Android app targets SDK 36. A pinned [AOSP SELinux policy](https://android.googlesource.com/platform/system/sepolicy/+/fa3eb773ce45c9c1a38a579f31799ffc00b85952/private/app_neverallows.te) blocks modern untrusted apps from `execve()` on files in `app_data_file`/`privapp_data_file`, with compatibility exceptions only for legacy target APIs through 28. Therefore copying the Termux executable into Aggregate's writable app-data directory is not a viable drop-in route. This static policy/source check was not exercised on the phone.
- **Assessment:** Termux is a current Node 24 Android binary source, but its package is not an Aggregate-embeddable `libnode.so` runtime or complete npm/CLI bundle. Reusing it requires a different, app-compatible packaging/launch design and dependency closure; this inspection does not qualify that design. The package bytes were not installed or executed, npm was not separately fetched, and repository signing/provenance, complete SBOM/license review, APK/AAB integration, 16 KB runtime, and production signing remain open. No NodeProbe, npm, CLI, or accessibility tests were run.

The 2026-11-23 package inspection supersedes only the 2026-11-20 statement below that the aarch64 `.deb` member inventory was not established. Contents for the other three ABI packages remain uninspected.

- **Assessment:** This closes the freshness question for a current Android Node distribution lead and confirms a matching separate npm package is published. It does not qualify as an Aggregate in-process runtime: it is a Termux-prefix standalone executable with external native dependencies, not `libnode.so`. The isolated APK subprocess smokes below show that this package line can launch from an Android app after repackaging, install one pure-JS package in app-private storage, and run its JS CLI on this 4 KB device. They do not verify product integration, lifecycle scripts, native addons, arbitrary CLI/TUI behavior, provenance/signing, full license/SBOM closure, or 16 KB device execution. A3.6/A4 remain open.

### 2026-11-26 isolated Android app-process smoke

- Built a throwaway, arm64-only, debug-signed Android APK in `/tmp/aggregate-node-apt-26.13.1/apk-probe` (application ID `io.github.aggregate.nodeaptprobe`, min SDK 24, target SDK 36). This is not the Flutter Aggregate app and did not modify repository source. The APK was 43,238,536 bytes and contained 11 runtime ELF files totaling 99,180,528 uncompressed bytes plus 9,744,645 bytes of npm runtime assets.
- The runtime ELF closure used Node 26.13.1 and Termux dependencies libc++ 30, OpenSSL 3.6.5, c-ares 1.34.9, ICU 79.1, SQLite 3.54.1-1, zlib 1.4, and libffi 3.8.1. All 11 packaged ELF files had `PT_LOAD p_align=0x4000` and matching file/virtual offsets modulo 16 KB; APK `zipalign -c -P 16 -v 4` also passed. This is static alignment evidence for this temporary APK, not a 16 KB device runtime result.
- Gradle's `jniLibs` packaging selected `.so` filenames and omitted Termux's versioned `.so.*` names. For this isolated experiment only, the dependency filenames plus ELF `DT_NEEDED`/`DT_SONAME` strings were normalized to unversioned `.so` aliases; the process received `LD_LIBRARY_PATH` pointing at Android's extracted `nativeLibraryDir`. npm assets were copied into app-private files before launching its CLI with Node. The APT package signature was not verified, and this temporary ELF rewrite is not a product-ready redistribution recipe.
- On the LGE AN10, Android 15 / API 35, 4 KB page-size device, cold launch returned `Status: ok` (`TotalTime: 492 ms`). The child process ran `v26.13.1 / android / arm64` with exit code 0; the npm CLI returned `12.2.3` with exit code 0. The smoke did not access the network, run `npm install`, load a native addon, or execute an application-specific CLI. Afterward the probe package was force-stopped and uninstalled, no probe package/PID remained, and the launcher was foreground again.
- **Assessment:** A standalone Node executable and bundled npm CLI can run as app-spawned child processes on this 4 KB device when their native dependency closure is included and adapted. This does not test `node::Start`/JNI or an in-process `libnode.so`, and it does not establish compatibility with the product's Flutter lifecycle or distribution rules. npm installation, representative CLI behavior, source provenance and redistribution licenses, production build/signing, and physical 16 KB execution remain open; A3.6/A4 do not close.

### 2026-11-26 Termux Node/npm app-process npm install and CLI follow-up

- **Asset packaging diagnosis:** The first isolated `npm install cowsay@1.6.0` failed before network access because `@sigstore/protobuf-specs/dist/index.js` could not load `./__generated__/envelope`. The files existed in the APT npm package and staged source assets, but the APK omitted 16 JS files under `__generated__`. Android Gradle's default asset ignore list includes `<dir>_*`; `!` suppresses a warning and is not an allow rule. The temporary probe explicitly set the remaining default ignore patterns without `<dir>_*`, preserving other default filters. The rebuilt APK then contained all 16 generated files; three non-runtime dotfiles remained excluded. See the official [AGP `ignoreAssetsPatterns` API](https://developer.android.com/reference/tools/gradle-api/9.3/com/android/build/api/dsl/AndroidResources#ignoreAssetsPatterns) and [AAPT asset-filter implementation](https://android.googlesource.com/platform/tools/base/+/90d7f32/sdk-common/src/main/java/com/android/ide/common/res2/DataSet.java).
- **TLS trust:** The first network attempt then failed with `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`. The stable APT index listed `ca-certificates` version `1:2026.11.05-1`, architecture `all`, size 110,148 bytes, SHA-256 `12fc350fc5ad638338b06b04835bce897615f8c93f96d30ac396cdb39b850c6b`; the downloaded `.deb` matched that index hash. Its `etc/tls/cert.pem` was 200,116 bytes, SHA-256 `427c064216761a1e72a8b30f0d954d08cb6e4435a82091fb865afd20c8497285`. The probe copied that PEM into app-private storage and set `NODE_EXTRA_CA_CERTS`; TLS certificate verification remained enabled. Node documents this variable as extending its well-known root CAs ([Node.js v26.13.1 CLI docs](https://nodejs.org/api/cli.html#node_extra_ca_certsfile)). APT repository signature verification was not performed.
- **4 KB device result:** Rebuilt the temporary arm64 debug APK (`io.github.aggregate.nodeaptprobe`, min SDK 24, target SDK 36), final size 43,361,941 bytes. APK `zipalign -c -P 16 4` passed; the 11 runtime ELFs were unchanged from the previous static review, where each `PT_LOAD` had `p_align=0x4000` and matching offset/address modulo 16 KB. On LGE AN10 / Android 15 / API 35 / arm64 / `PAGE_SIZE=4096`, one foreground cold launch ran Node `v26.13.1 / android / arm64` and npm `12.2.3`, both exit 0. npm installed `cowsay@1.6.0` into the probe's app-private directory with `--ignore-scripts --no-audit --no-fund`; 41 packages were added in 13 seconds. Running the package's `cli.js` through Node printed `Aggregate Android npm smoke` in the expected cowsay output and exited 0.
- **Limits and cleanup:** No lifecycle script, native addon, `ncm-cli`, TUI, or Aggregate product adapter was run. This is a temporary standalone Node child process with Termux libraries aliased and `DT_NEEDED`/`DT_SONAME` names rewritten, not an in-process `libnode.so` integration or production redistribution plan. The CA and npm package hashes match the HTTPS-fetched APT index, but the repository signature, complete redistribution license/SBOM review, and legal approval remain open. The package was force-stopped/uninstalled; no probe PID or ADB reverse remains and the launcher was foreground again. A3.6/A4 product npm/CLI gates remain open.

## Source and maintenance evidence

- Node.js’s [official `v24.22.3` release](https://nodejs.org/en/blog/release/v24.22.3/) identifies it as the Node 24 LTS security release.
- The current [Termux `nodejs-lts` build recipe](https://raw.githubusercontent.com/termux/termux-packages/master/packages/nodejs-lts/build.sh) pins `TERMUX_PKG_VERSION=24.22.3`, fetches the official Node source tarball `https://nodejs.org/dist/v24.22.3/node-v24.22.3.tar.xz`, and pins its SHA-256 to `48ca3aa8a9b02133356922ef4fc80200e00598c80a4ef446f7c39a459222593d`.
- The same recipe maps Termux `aarch64`, `arm`, `i686`, and `x86_64` to Node targets `arm64`, `arm`, `ia32`, and `x64`; it configures `--dest-os=android`, applies Termux package patches, and installs through Node’s `tools/install.py` into `$TERMUX_PREFIX`. Runtime dependencies are `libc++`, OpenSSL, c-ares, ICU, SQLite, and zlib.
- The recipe configures Node with `--without-npm`, sets `TERMUX_PKG_RECOMMENDS="npm"`, and its package script says npm is installed separately for `nodejs-lts` versions starting at 24.13.0. The `nodejs-lts` binary package alone therefore does not include the npm CLI; an Android app would need to package and integrate the separate Termux npm package as well.
- The recipe identifies the upstream Node source version, but does not declare a nodejs-mobile revision or expose a `process.versions.mobile` value; that runtime field was not measured here.
- The recipe names maintainer Yaksh Bariya and sets automatic version updates off. Its maintainer comment says the package is manually updated because one-architecture builds take about two hours and that tests are run on updates. The live APT index observed on the checked date contains 24.22.3 packages for all four advertised architectures. These are concrete maintenance signals; they do not establish a release SLA or a separate Node-for-mobile support commitment.
- The package repository’s `Packages` records expose package filenames, sizes, dependencies, and SHA-256 values. This survey did not independently verify the repository signing key, reproduce the builds, or inspect attestations/SBOMs.

## Embedding and release limits

Termux documents its package prefix as `/data/data/com.termux/files/usr`, and says packages are built for Termux’s root filesystem and have paths rewritten for that prefix ([filesystem layout](https://github.com/termux/termux-packages/wiki/Termux-file-system-layout), [execution environment](https://github.com/termux/termux-packages/wiki/Termux-execution-environment)). Android’s app-specific storage documentation says internal app data is private to that app and other apps cannot access it ([Android Developers](https://developer.android.com/training/data-storage/app-specific)). A Flutter app cannot depend on files installed inside Termux’s private prefix as though they were its own APK libraries.

The surfaced artifact contract is an architecture-specific Termux `.deb` package. The recipe declares an Android Node build and Termux-prefix installation; it does not declare a Flutter/Java embedding API, JNI bridge, or a `libnode.so` SDK release. Reuse would require a separate packaging and integration effort that resolves Termux prefix assumptions and dependencies. The exact `.deb` file inventory was not established in this survey: a read-only download attempt timed out partway through, so no claim is made about its internal member list.

This evidence also does not establish 16 KB ELF load-segment alignment, APK ZIP alignment, or execution on a physical 16 KB-page device. No package was installed or executed, and no accessibility or other tests were run. Treat Termux as a **current-source/current-binary lead**, not as a qualified Aggregate embed-ready runtime: the package installs into Termux’s private prefix, npm is separate, and the checked artifacts/recipe do not expose a Flutter/JNI `libnode.so` embedding SDK. A3.6 still needs a deliberate embedding path, complete source-to-binary and license review, target ABI packaging, and the project’s 16 KB and signing checks.

This was a bounded check of Termux’s official main APT repository and `termux-packages` source, alongside the prior project checks of nodejs-mobile, fogtape, and digidem. It does not establish that all Android Node providers or third-party repositories were surveyed.
