## Representation is distinct from evidence

[CycloneDX 1.6 JSON](https://cyclonedx.org/docs/1.6/json/) permits either a list of SPDX/named license objects or a single SPDX expression in `licenses`, not both forms together. The [versioned 1.6 schema](https://github.com/CycloneDX/specification/blob/master/schema/bom-1.6.schema.json) provides no AND/OR operator on the list branch, so use an SPDX expression when encoding cumulative terms or alternatives. [SPDX expressions](https://spdx.github.io/spdx-spec/v2.3.1/SPDX-license-expressions/) define `AND` for cumulative requirements, `OR` for a choice, and allow a document-local `LicenseRef-...` for a license absent from the SPDX list. A custom reference must have a stable documented meaning and exact associated text for recipients; its name is not evidence of a grant. CycloneDX expression objects in 1.6 do not themselves carry per-reference license text; the [CycloneDX maintainer clarification](https://github.com/CycloneDX/specification/discussions/713) says per-expression text support arrived in 1.7. A separate traceable notice or separately scoped named-license component is therefore needed for the custom text in this 1.6 BOM. A schema-valid string alone does not demonstrate recipient interoperability, complete license scope, or compliance. Verify actual generator and consumer behavior with the 1.6 schema and expression parser before changing metadata; do not assume a custom reference is an SPDX-listed `id`.
