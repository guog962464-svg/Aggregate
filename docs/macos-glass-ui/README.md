# macOS 玻璃点阵 UI：分阶段适配流程与验收标准

> 日期：2026-11-14 · 设计基线：revision 5
>
> 状态：UI-0～UI-4 已完成并分别提交；UI-5 功能与无障碍回归、UI-6 原生性能与最终验收继续按阶段实施、验收、分别提交并推送。
>
> 平台：只在 macOS 启用新设计；共用 Flutter/Dart 组件保持平台无关。

## 1. 目标与固定边界

以现有太阳/月亮切换按钮的玻璃质感为整套 UI 的材质基准，统一背景、点阵颗粒、内部散射和局部光弧。每类按钮具有符合功能的静置与点击动作，布局按用户的操作顺序组织。

- 原主题按钮复用现有实时实现；尺寸与位置优先在父布局调整。任意拖动、反向、取消、回弹、太阳/月亮内部变化、光效、偏好与系统模式的逻辑不变。仅呈现适配的范围与验证要求见 UI-0/UI-1。
- 所有新按钮的内部图案使用同一套圆角点阵；运行、刷新不再单独使用连续实心三角或矢量弧线。
- 背景以主题按钮所在的中性天空与颗粒背景为准，侧栏、主区和外观设置区使用同一背景坐标体系，消除矩形背景接缝。
- 静置与点击有各自的动作，但共享相位、能量包络和采样时刻。动画合并不改变业务回调、权限、禁用或运行状态。
- 设计稿中的示例结果、连接、播放和 Host 状态仅供设计演示。接入时使用当前 Runtime 和会话状态，动画完成不能宣布业务成功。
- 不使用固定帧序列、视频或 WebView 回放完成适配。不改 Android 的主题过渡与交互行为，不扩展运行端协议。

本方案细化当前设计稿的落地要求，不声明原视频已经逐帧零误差。原视频拟合的已知限制继续见[主题切换说明](../theme-switch-reference.md)。

## 4. 实施约定

1. 先完成独立原生样本，再接入真实页面；沿用现有状态来源，不复制第二套 Runtime 或音乐会话。
2. 每阶段只运行与改动相关的必要检查；UI-5/UI-6 再做完整回归与原生验收。修改测试期望不能替代修复回归。
3. 新组件先选择适合 Flutter 的绘制方式。设计稿的共享 WebGL/RAF 是浏览器实现细节；Flutter 需要实现对应的材质、单时钟、缓存与生命周期约束。
4. 禁用、忙碌、成功、失败、取消、超时等状态由现有业务决定。按钮装饰不得延迟提交、自动重试或改变权限确认。
5. 每个完成阶段形成可独立回退的任务提交，按项目规则正常推送并核对两个远端。只纳入本阶段文件，保留用户及其他任务改动。

## 5. 验收记录格式

阶段实施时新建或更新 `docs/macos-glass-ui/acceptance-record.md`。结果只按实际操作和证据填写。每项使用以下字段：

| 字段 | 要求 |
| --- | --- |
| 项目 | 对应阶段与验收编号，例如 UI-3.3 |
| 版本 | 本地 commit、设计 revision/SHA、相关未提交改动、Flutter/Dart/锁文件版本 |
| 环境 | Mac 型号、系统、构建模式、显示器、实际刷新率、窗口逻辑尺寸、DPR、外观、减少动态效果 |
| 操作 | 可重复的输入、顺序、时间点和样本内容 |
| 预期/实际 | 分别写明；未知、未测、阻塞不能写通过 |
| 证据 | 测试命令/退出码、脱敏日志、截图、录屏、帧时统计的可定位路径 |
| 结果 | 待验收 / 通过 / 失败 / 不适用；不适用要写原因和影响范围 |

自动化测试、fixture 预览、真实 Runtime 验证和用户视觉确认分别记录，不能相互代替。验收过程中发现设计变化，先更新设计基线及受影响标准，再重新验证对应项目。
